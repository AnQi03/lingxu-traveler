# AI 辅助游戏开发模式调研

> 调研时间：2026-05-22
> 目的：学习业界 AI+游戏开发的最佳实践，改进灵墟旅商的开发效率

---

## 一、主流 AI 开发游戏的三种模式

### 模式 A：AI 写代码 + 人验收（Cursor / Claude Code 模式）

```
人：写需求描述 / 设计文档
  ↓
AI：生成代码
  ↓
人：在引擎中运行测试
  ↓
人：反馈问题 → AI 修 → 再测
  ↓
人：验收通过 → 提交
```

**代表案例**：
- Cursor + Godot 社区：大量独立开发者用 Cursor 写 GDScript，人做架构决策
- Pieter Levels（levelsio）：用 AI 写 90% 代码，人只做产品决策和最终验收

**优点**：人保持控制权，AI 做重复劳动
**缺点**：往返次数多，代码质量依赖 prompt 质量

---

### 模式 B：全自动生成（Vibe Coding 极端版）

```
人：一句话描述需求
  ↓
AI：生成完整项目（代码+资源+场景）
  ↓
人：跑起来看看
```

**代表案例**：
- "用 AI 5 分钟做一个 Flappy Bird" — 简单小游戏可行
- 各种 AI 游戏生成比赛（GMTK Game Jam + AI）

**优点**：极快
**缺点**：只能做简单游戏。复杂游戏（RPG/模拟经营）必定失控，因为 AI 缺少全局设计能力

---

### 模式 C：混合模式（设计人驱动 + AI 执行 ⭐推荐）

```
人：设计文档 + 数值表（「权威源」）
  ↓
人：每个功能的 mini-spec（改什么/预期效果/验收标准）
  ↓
AI：生成代码 / 生成美术
  ↓
人：在编辑器验证 → 通过或反馈
  ↓
迭代直到满意 → 提交
  ↓
人：更新「权威源」（设计文档/数值表/TASKS.md）
```

**代表案例**：
- 2024-2025 年成功的 AI 辅助独立游戏项目（多数不公开细节但模式一致）
- "The AI is my junior programmer, not my game designer"

**优点**：
- 人保持设计权威，AI 做执行
- 每次迭代范围小、可验证
- 不会出现「AI 把设计带歪了越改越远」

**缺点**：对人的设计能力要求高，需要人先想清楚再让 AI 动手

## 二、关键教训（来自社区和实战）

### 教训 1：AI 擅长实现，不擅长设计

> "让 Claude 设计游戏系统 → 得到缝合怪。让 Claude 实现我设计好的系统 → 10 倍效率。"

**我们的问题**：有时候我直接按你的需求写代码，但如果你没给详细的 mini-spec，我可能理解偏差 → 做出来不对 → 返工。

**改进**：每个任务前必须写 mini-plan → 你确认 → 开工。

---

### 教训 2：上下文窗口是瓶颈

> "200K token 上下文看起来很多，但一个中型 Godot 项目轻松超过。AI 必须在有限上下文中工作。"

**我们的问题**：之前每次改代码，我会读好几个文件来「了解上下文」，消耗大量 token。然后你还得等我读完。

**改进**：
- 已有 lingxu-token-saving 策略（script_create 替代多次 patch、batch_execute 合并操作）
- 新增：mini-plan 里明确改哪些文件，只读相关文件
- 项目状态靠 TASKS.md + project-tracker 而不是每次重新扫描

---

### 教训 3：快速验证 > 完美代码

> "写 100 行代码 → 立刻跑 → 看效果 → 修正。比写 500 行 → 跑 → 全是 bug → 修半天 快得多。"

**我们的现状**：已经有 project_run + logs_read 验证循环，这个做得不错。

**改进空间**：mini-plan 阶段就定义好验收标准，验证时对照检查，不遗漏。

---

### 教训 4：设计文档是 AI 的「地图」

> "没有设计文档的 AI 开发 = 让出租车司机在没有导航的情况下开到没去过的地方。"

**我们的优势**：我们有 42 份设定文档 + 设计参考，这在 AI 辅助开发中是极大的优势。

**问题**：改代码时我没有主动查阅这些设计文档，凭记忆和理解来做。

**改进**：mini-plan 阶段标注「参考设计文档：xxx.md」，让我在动手前先读相关设定。

---

### 教训 5：人必须保持「验收者」角色

> "AI 说 '我做完了' 的时候，代码可能有 5 个 bug。人必须亲自跑、亲自测。"

**我们的现状**：你测试、反馈、我修。这个循环是对的。

**改进**：我在告诉你「去测吧」之前，必须先 project_run + logs_read 确认零编译错误。这是铁律。

## 四、改进方案（整合进我们的工作流）

基于以上调研，在已有的工作流上增加以下规则：

### 规则 1：Mini-Plan 模板
每次改代码前，我输出：
```
📋 Mini-Plan
- 改哪些文件：xxx.gd, yyy.gd
- 预期效果：玩家按X键时...
- 验收标准：1) 编译零报错 2) X键触发Y 3) 不影响已有功能
- 参考文档：设定文档/xxx.md
```
你确认 → 开工。

### 规则 2：一次只做一件事
一个任务 ≤ 3 个文件修改。如果需要改 5+ 文件，拆成两个任务。

### 规则 3：设计文档是「地图」
每次 mini-plan 标注参考哪些设定文档，我先读再写代码。

### 规则 4：Pre-Flight 铁律（已有，强化）
改完代码 → project_run → logs_read 零报错 → 才能说「去测吧」→ commit。

### 规则 5：任务完成后更新 TASKS.md
完成后标记 ✅，写一行验证结果。

## 五、总结

业界最成功的 AI 辅助游戏开发模式是 **「混合模式」**：人做设计师，AI 做执行者。

我们的项目已经具备了关键优势（42 份设定文档 + 成熟的验证循环），差的只是**前置规划**和**任务追踪**两个环节。TASKS.md 今天已经建立，mini-plan 规则从下一个任务开始生效。

预期效果：减少「做出来不对」的返工 → 减少沟通往返 → 每个任务更快闭环。
